# TwinCoach hacomono API相談用1枚資料

作成日：2026-06-08  
対象：本部・井上さん・濱口さん・林さん、将来的にhacomono担当者

---

## 1. 目的

| 項目 | 内容 |
|------|------|
| TwinCoachの位置づけ | hacomonoを置き換えるものではない。hacomonoの会員/予約/契約データを活用し、退会予防・LTV改善・現場行動支援へつなげる補助レイヤー |
| API連携の方針 | PoC後に必要性を確認してから行う。PoC中はCSV/限定データで検証する |
| 既存運用との関係 | hacomono・kintoneの既存運用は止めない |

---

## 2. API連携の基本方針

- いきなり本番API連携しない
- まずCSVでPoCを実施し、現場価値を確認する
- PoCで必要な項目と更新頻度を確認してから連携項目を決定する
- API連携は必要最小限の項目から段階的に進める
- 既存のhacomono/kintone運用は止めない
- 本番連携前に権限・セキュリティ・費用を必ず確認する

---

## 3. 連携したいデータ候補

| データ | 利用目的 | 利用画面 | 優先度 | 備考 |
|--------|----------|----------|--------|------|
| 会員基本情報 | 会員詳細表示・検索 | 店舗/オーナー/本部 | 高 | 氏名・連絡先・生年月日など |
| 所属店舗 | 店舗別データスコープ制御 | 全ロール | 高 | ロール権限と紐づけ必須 |
| 契約プラン | LTV計算・収益分析 | オーナー/本部 | 高 | プラン種別・単価 |
| 入会日/退会日/休会情報 | 在籍期間・リスク判定 | 全ロール | 高 | 退会予防の基礎データ |
| 予約情報 | 来店頻度・行動傾向把握 | 店舗/オーナー | 中 | 予約件数・直近予約日 |
| 来店履歴 | セッション実績・定着率確認 | 店舗/オーナー | 中 | 月別来店回数など |
| キャンセル情報 | リスク検知・介入タイミング判断 | 店舗/オーナー | 中 | キャンセル率・連続キャンセル |
| 担当トレーナー | セッション入力・担当割り当て | 店舗 | 中 | トレーナー紐づけ管理 |
| 会員ステータス | アクティブ/休会/退会の判定 | 全ロール | 高 | ステータス変更日も必要 |
| 支払い/未払い情報 | 収益リスク検知・LTV算出 | オーナー/本部 | 低 | 個人情報取り扱い要確認 |

---

## 4. 連携後に実現したいこと

- **本部**：全店舗のLTV傾向・退会リスク傾向を横断確認できる
- **オーナー**：管轄店舗の会員状況・リスク会員・売上状況をダッシュボードで確認できる
- **店舗**：会員詳細・介入タスク・セッション入力にリアルタイムデータを活用できる
- **SV**：店舗別の課題や支援優先度をデータに基づいて判断できる
- **全体**：APIによりCSV手動更新作業を削減し、データ鮮度を確保できる

---

## 5. API相談前にTwinCoach側で準備すること

- [ ] PoC結果（CSVで検証した項目と得られた知見）
- [ ] CSVで検証できた項目・できなかった項目の整理
- [ ] API連携が必要な理由（CSVでは対応できない理由）
- [ ] 利用画面ごとの必要データ一覧
- [ ] 更新頻度の案（リアルタイム/1日1回/週1回など）
- [ ] 権限仕様の概要（ロール別のデータスコープ設計）
- [ ] 個人情報取り扱い方針（保存範囲・暗号化・アクセス制御）
- [ ] 開発/検証環境の構成（sandbox利用の可否）
- [ ] 本番環境の想定構成（Supabase連携含む）
- [ ] 障害時の切り戻し方針（API停止時にCSVで代替できるか）

## 6. hacomonoに確認したい主な質問

| 確認項目 | 内容 |
|----------|------|
| API利用条件 | 契約プラン・利用開始の要件 |
| 取得可能データ | 会員/予約/来店/契約/支払い情報の提供範囲 |
| レート制限/更新頻度 | 1日あたりのリクエスト上限・最小更新間隔 |
| sandbox/検証環境 | 本番データを使わず開発できる環境の有無 |
| 認証方式 | OAuth/APIキー/IPホワイトリストなど |
| 店舗/ロール単位の取得制御 | 店舗単位でのデータスコープ制御が可能か |
| 費用 | API利用費用・従量課金の有無 |
| 申請手続き | 申請から利用開始までのフローと期間 |
| 障害/仕様変更時の対応 | 通知方法・変更通知のリードタイム |

---

## 7. 避けるべき進め方

- 「とりあえずAPIを使いたい」という段階で相談しない
- 連携項目が未整理のまま相談に臨まない
- PoC前に本番データをすぐ使おうとしない
- hacomonoを置き換える前提で話を進めない
- kintoneを即廃止する前提で話を進めない
- 全店舗・全会員を一気に連携しようとしない

---

## 8. 一言まとめ

> TwinCoachのhacomono API連携は、PoC後に必要性が確認できた項目から段階的に進める。まずはCSV/限定データで現場価値を検証し、その結果をもとに、取得データ・更新頻度・権限・費用・セキュリティを整理してからhacomonoへ相談する。
