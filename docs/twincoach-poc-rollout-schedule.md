# TwinCoach PoC導入スケジュール案

**サブタイトル：CSVで小さく検証し、PoC後にAPI連携範囲を決める**

作成日：2026年6月6日
対象：林さん提案用・井上さん＋濱口さんMTG後の次ステップ整理

---

## 結論

| 方針 | 内容 |
|------|------|
| **いきなり全店舗導入しない** | 1〜2店舗に絞ってPoCを実施する |
| **いきなりAPI連携しない** | CSV/限定データで開始し、PoC後に連携判断する |
| **まず2〜4週間でPoC** | 現場運用に乗るかを小さく検証する |
| **現場価値を確認してから本導入** | 入力負担・介入タスクの有用性・本部判断材料になるかを評価する |

## PoC対象店舗の条件

- 会員数が多すぎない（初期データ投入・運用確認がしやすい）
- 店舗スタッフが協力的（入力・フィードバックに対応できる）
- 入力負担を検証しやすい（スタッフの日常業務が見えやすい）
- 退会予防・来店頻度の課題が見えやすい（介入タスクの有用性を確認しやすい）
- 不具合が起きても既存運用への影響が小さい
- CSVデータを準備しやすい（hacomono/kintoneからの出力が可能）
- SV/本部が状況確認しやすい（遠隔確認・フォローが現実的）

## PoCで使うデータ

| データ種別 | 目的 | PoC必要 | CSVで開始 | API連携候補 | 注意点 |
|------------|------|---------|----------|------------|--------|
| 会員情報CSV | 会員登録・リスク判定の基盤 | ◎必須 | ○ | ○ | 個人情報のため最小項目に絞る |
| 予約/来店履歴CSV | 来店頻度・離脱傾向の把握 | ◎必須 | ○ | ○ | 期間を絞って投入（直近3〜6ヶ月） |
| セッション履歴CSV | トレーニング進捗・介入タスク生成 | ○推奨 | ○ | ○ | 既存カルテの代替ではなく補助として使う |
| タスク情報 | 介入アクションの管理 | ◎必須 | TwinCoach内で生成 | △後回し | PoCではシステム側で生成・手入力で管理 |
| カウンセリング情報 | 目標・健康状態の把握 | △任意 | ○（一部） | △後回し | 停止すると困る機能のため置き換えない |
| 売上/未払い情報 | 収益管理・LTV把握 | △任意 | ○（一部） | △後回し | PoCでは参考程度。本番連携はPoC後に判断 |

## PoC中の役割分担

### 本部
- **やること**：全体のPoC進捗管理、方針判断
- **見る画面**：本部ダッシュボード（全店舗サマリー）
- **判断すること**：PoCを続けるか、API連携に進むか
- **確認頻度**：週1回以上のダッシュボード確認

### 井上さん／SV
- **やること**：現場運用の橋渡し、店舗フォロー、利用状況ヒアリング
- **見る画面**：本部・オーナーダッシュボード、店舗詳細
- **判断すること**：現場の入力負担・介入タスクの使いやすさ
- **確認頻度**：週2〜3回。フィードバックを都度収集

### 濱口さん／ツール・サービス担当
- **やること**：CSV準備・hacomonoデータ出力・ツール連携確認
- **見る画面**：CSVインポート画面、設定画面
- **判断すること**：API連携の現実性・必要項目・費用感
- **確認頻度**：PoC準備時に集中対応。PoC中は随時

### オーナー
- **やること**：管轄店舗の状況確認、スタッフへの周知・協力依頼
- **見る画面**：オーナーダッシュボード、管轄店舗詳細
- **判断すること**：店舗の運営改善につながるかどうか
- **確認頻度**：週1〜2回

### 店舗スタッフ
- **やること**：セッション入力、介入タスク確認・実行、フィードバック報告
- **見る画面**：店舗ダッシュボード、会員一覧、セッション入力画面
- **判断すること**：入力のしやすさ、現場で使えるかどうか
- **確認頻度**：都度（セッションごと）

### 小野／TwinCoach側
- **やること**：CSV投入・環境整備・不具合対応・フィードバック反映
- **見る画面**：管理画面全般、ログ
- **判断すること**：改善優先度、API連携の技術的実現性
- **確認頻度**：毎日確認。週次でフィードバックまとめ

## PoCで検証する指標

| 指標 | 確認方法 |
|------|---------|
| 現場スタッフが使えるか | スタッフの入力継続率・操作ログ |
| 入力負担が重すぎないか | スタッフへのヒアリング・入力時間の体感 |
| セッション入力が現場運用に合うか | 既存カルテと比較した入力項目の過不足 |
| 介入タスクが役に立つか | タスク完了率・スタッフの体感評価 |
| 高リスク会員に早く気づけるか | リスク判定の精度・見落としの有無 |
| オーナーが管轄店舗の状況を把握できるか | ダッシュボード閲覧頻度・使い方のヒアリング |
| 本部が施策判断に使えるか | 本部担当者の活用度・判断速度の変化 |
| API連携すべきデータ項目が明確になるか | PoC後のデータ不足・手作業の洗い出し |

## スモールスタート方針

佐々木さんのフィードバックを踏まえた原則：

- **最初から全店舗導入しない**：1〜2店舗に絞り、問題の影響範囲を最小化する
- **既存機能を止めない**：hacomono・kintoneは継続利用。TwinCoachは補助レイヤーとして使う
- **カルテ等の重要機能を最初に置き換えない**：停止すると困る機能はPoC後に検討する
- **低リスクな範囲から検証する**：まずはセッション入力・介入タスク・ダッシュボード確認から
- **設計書・段階導入・移行計画を重視する**：PoC結果を踏まえて順序立てて進める
- **環境整理を先行させる**：本番環境・権限・契約条件はPoC後に整理する

## 切り戻し方針

| リスク | 対応方針 |
|--------|---------|
| TwinCoachに不具合が発生 | 既存hacomono/kintone運用に即時戻せる設計にする |
| データ連携の問題 | PoCはCSV/限定データにする。自動同期はAPI連携後まで行わない |
| 個人情報の取り扱い | 本番個人情報は最小限。PoC期間中は必要最低限の項目のみ |
| 現場の混乱 | 既存ツールを止めずに並行運用。「TwinCoachが使えなくなっても現場は止まらない」状態を維持 |
| API連携の遅延 | API連携の判断はPoC後。PoC中はCSVで代替し、影響を受けない |

## PoC後の判断基準

| 判断軸 | 判断できる状態 |
|--------|--------------|
| 継続して使う価値があるか | 現場スタッフ・オーナー・本部それぞれに「使ってよかった」が出ているか |
| 入力負担が許容範囲か | 既存業務への上乗せが最小限で、スタッフが自発的に使えるか |
| 本部/オーナーが見たい情報になっているか | ダッシュボードで意思決定・指示ができるか |
| API連携すべきデータが明確か | 手作業の洗い出し・不足項目のリストが揃っているか |
| 導入リスクを管理できるか | セキュリティ・権限・契約の整理ができているか |
| 設計書・環境整理を進められるか | hacomono API確認・費用・スコープが明確になっているか |

## まとめ

TwinCoachは、いきなり本番API連携や全店舗導入を行うのではなく、まずは1〜2店舗・CSV/限定データで小さくPoCを行い、現場価値・入力負担・本部/オーナーの判断材料として使えるかを確認します。PoC後に、必要なAPI連携範囲・費用・セキュリティ要件を整理し、本導入判断へ進む方針です。
