# TwinCoach 契約/料金/責任範囲整理

> STEP11 — 論点整理用たたき台 | 2026-06-07 作成  
> 対象：林さん提案・佐々木さんフィードバック反映・PoC/本導入前の整理用

---

## 注意書き

- **本資料は契約書そのものではない。** PoC/本導入前に整理すべき論点一覧です
- **最終的な契約形態・条項・免責範囲は専門家（弁護士・司法書士）の確認が必要です**
- ELEMENT専用開発として扱うか、汎用SaaSとして扱うかで契約形態・権利関係・料金体系が大きく変わります
- 本資料の内容は口頭合意・メモの段階を想定しています。法的拘束力はありません

## 結論

| 方針 | 内容 |
|---|---|
| **PoC段階は小さく安全に** | 口約束ではなく、書面またはメールで合意内容を残す |
| **本導入前に契約形態を決める** | 請負・準委任・月額SaaSのどれか、またはその組み合わせを明確にする |
| **追加開発と保守を分ける** | 保守範囲に含めるものと、都度見積もりが必要なものを事前に決める |
| **個人情報・データ責任を明確にする** | 誰がどのデータを管理し、不具合時は誰が責任を負うかを決める |
| **BtoB契約として扱う** | 個人開発の延長ではなく、ビジネス上の合意として整理する |

## 2. 契約形態の比較

| 契約形態 | 内容 | 向いているケース | メリット | リスク/注意点 | TwinCoachでの考え方 |
|---|---|---|---|---|---|
| **請負契約** | 成果物の完成を約束する。完成しなければ報酬が発生しない | 機能単位の開発（例：API連携機能）| 成果が明確で発注側の安心感が高い | 仕様変更のたびに再契約が必要。TwinCoach側の負担大 | 追加開発の一部に適用可能。保守には不向き |
| **準委任契約** | 業務の遂行を約束する。成果物の完成保証はない | 継続的な運用改善・保守・PoC伴走支援 | 柔軟に対応できる。仕様変更に強い | 成果が不明確になりやすい。費用と成果の整合が必要 | PoC期間中・保守運用フェーズに適している |
| **月額SaaS利用契約** | ソフトウェアをサービスとして月額で提供する | 汎用SaaSとして複数法人に提供する場合 | スケーラブル。料金が安定 | 機能仕様はTwinCoach側が決定権を持つ。ELEMENT専用カスタマイズに制限 | 汎用SaaSとして展開する場合の本導入契約形態 |
| **保守契約** | 定義された保守範囲内の対応を月額で提供する | 本導入後の継続運用 | 費用が予測しやすい。継続的な関係を維持できる | 保守範囲を明確に定義しないと範囲外要望が多発する | 本導入後に月額利用料と合算または別契約で締結 |
| **追加開発契約** | 保守範囲外の機能開発を都度見積もりで行う | API連携・FC精算・顧客チャットなどの高度機能 | 費用・スコープを事前確定できる | 見積もり・合意のプロセスが増える | 追加機能はすべてこの形で管理することを推奨 |

## 3. PoC段階の合意事項

| 項目 | 合意内容 | 確認すべきこと |
|---|---|---|
| PoC対象店舗 | 1〜2店舗に限定する（スケジュール資料参照）| 店舗名・担当者名を書面で確認 |
| PoC期間 | 2〜4週間を目安（7月中を想定）| 開始日・終了日を書面で確認 |
| 利用データ範囲 | CSVインポートによる限定データのみ | 本番個人情報の扱いをPoC前に確認 |
| 個人情報の扱い | 必要最小限のデータに絞る。氏名は仮名またはIDで管理も検討 | 個人情報保護法上の取り扱い責任者を明確にする |
| CSV/限定データで始めること | hacomono APIはPoC中は使用しない | CSV形式・列名をPoC前に合意する |
| API連携はPoC後判断 | API連携の可否はPoC結果を見て決める | hacomono API利用可否は濱口さんに事前確認 |
| PoC中の不具合時対応 | 不具合発生時は既存運用（hacomono/kintone）に戻す | 報告ルート・対応時間をPoC前に確認 |
| 既存運用を止めないこと | hacomono/kintoneはPoC中も継続稼働 | TwinCoachはあくまで補助レイヤー |
| PoC結果の扱い | 結果はELEMENT・TwinCoach双方で共有する | 結果の公開範囲を確認 |
| PoC後に本導入を保証しないこと | PoCは価値検証であり、本導入の義務は発生しない | この点を書面またはメールで明示する |

## 6. 保守範囲整理

### 保守に含める候補（月額利用料の範囲内）

| 内容 | 補足 |
|---|---|
| 軽微な不具合修正 | 表示崩れ・計算ミス・操作エラーなど明らかなバグ |
| 表示崩れ修正 | PC/スマホ表示の崩れ・文字化け |
| CSV項目の軽微調整 | 列名の変更・マッピングの微調整（大幅な変更は除く）|
| 操作説明 | メール・チャットによる操作方法の案内（月に数回程度）|
| 月次の軽微改善 | 小さなUI改善・ラベル変更・並び順の調整 |

### 保守に含めない候補（追加開発として別見積もり）

| 内容 | 補足 |
|---|---|
| 新機能開発 | 既存機能にない新たな画面・機能の追加 |
| API連携追加 | hacomono・kintoneなどとのAPI連携 |
| FC精算機能 | フランチャイズ間の精算機能 |
| 顧客チャット | 会員との1:1メッセージ機能 |
| 大幅な画面変更 | レイアウト・フロー・項目構成の大規模変更 |
| 既存業務置き換え | hacomono/kintoneの機能を完全にTwinCoachで代替する開発 |
| 外部システム仕様変更対応 | hacomonoのAPI仕様変更・CSV形式変更への対応 |

## 7. 追加開発の扱い

| 項目 | 内容 |
|---|---|
| 追加開発は都度要件整理する | 要望を受けたらそのまま実装せず、要件・スコープ・費用を整理してから進める |
| 見積もり対象にする | 追加開発はすべて見積もりを提示し、書面または口頭で合意してから着手する |
| 優先度を決める | 複数の要望がある場合、ELEMENTとTwinCoach双方で優先度を合意する |
| PoC中の要望管理 | PoC中に発生した要望は「即実装」と「本導入後検討」に分類する。PoC中の機能追加は原則行わない |
| 高リスク機能の別管理 | FC精算・顧客チャット・API本番連携は通常の追加開発とは分けて、個別に要件定義・契約・リスク評価を行う |

## 8. データ/個人情報責任

| 項目 | 方針 |
|---|---|
| PoCでは最小限のデータにする | 氏名・来店日・リスクスコアなど必要最小限に絞る。大量の個人情報をPoC環境に入れない |
| 本番個人情報を大量に扱わない | PoCではデモデータ・匿名データを優先する |
| CSVファイルの管理者を決める | ELEMENTが管理するCSVファイルの保管・送受信ルールを合意する |
| 個人情報の保存範囲を決める | TwinCoachに保存する項目・期間をPoC前に確認する |
| API連携後の保存/参照方針を決める | hacomono APIで取得したデータをTwinCoach DBに保存するか、都度参照のみにするかを本導入前に決める |
| 退職者/異動者のアカウント停止ルールを決める | スタッフが退職・異動した場合のアカウント無効化フローをELEMENT側で決める |
| データ削除/アーカイブ方針を決める | 退会会員・退職トレーナーのデータ保存期間と削除手順を決める |

## 9. 障害時/不具合時の扱い

| 項目 | 方針 |
|---|---|
| PoC中はhacomono/kintoneを止めない | TwinCoachはあくまで補助レイヤー。既存運用が最優先 |
| TwinCoach不具合時は既存運用へ戻す | TwinCoachが使えなくなっても業務が止まらない体制を維持する |
| 障害報告ルートを決める | 誰が・どこに・どの方法で（チャット/メール）報告するかをPoC前に決める |
| 対応時間を決める | 平日の対応時間帯（例：10〜18時）と緊急時の対応可否を確認する |
| 重要度を分類する | 業務停止レベル（Critical）/ 機能限定（Major）/ 軽微な表示崩れ（Minor）の3段階を定義する |
| 本導入前にSLAの要否を検討する | 本導入後に業務上重要な機能が増えた場合、SLA（対応時間保証）の設定を検討する |
| クリティカル機能は最初に置き換えない | 不具合が起きると業務が止まるような機能（売上管理・予約管理）は段階的に移行する |

TwinCoachはPoC段階では小さく安全に検証し、本導入前に契約形態・料金・保守範囲・障害時対応・データ管理責任を明確にする。特に追加開発、API連携、FC精算、顧客チャットなどは通常利用とは分けて契約/見積もり対象として扱う。
