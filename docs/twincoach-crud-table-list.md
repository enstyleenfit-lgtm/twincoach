# TwinCoach CRUD/テーブル一覧

> STEP10 — 設計たたき台 | 2026-06-07 作成  
> 本資料はPoC/本導入前の設計整理用です。本番DB定義の確定版ではありません。

---

## 結論

- TwinCoachでは会員・店舗・トレーナー・セッション・タスク・カウンセリング・売上・在庫・CSVインポートなど多様なデータを扱う
- PoCでは全データを本番DB化せず、CSV/限定データで価値検証を行う
- 本導入前に、テーブル定義・項目定義・CRUD権限・保存責任範囲を確定する必要がある
- hacomono/kintoneと役割が重複するデータ（会員情報・予約・売上など）は、どちらを「正」とするかを事前に決める必要がある

## 3. PoCで扱うデータ

### PoC優先（価値検証に必要）

| データ | 理由 |
|---|---|
| 会員 | コアデータ。継続率・LTVの計算基盤 |
| 店舗 | マルチ店舗対応の基盤 |
| トレーナー | タスク・セッションの担当者紐付けに必要 |
| セッション記録 | トレーナーの行動記録。改善提案の根拠 |
| 介入タスク | PoC価値の中心。自動提案→実行→効果測定 |
| リスクスコア | 離脱予測の可視化。意思決定支援 |
| LTV指標 | 収益改善の根拠データ |
| CSVインポート | 既存データ（hacomono）取り込みの主手段 |
| お知らせ | HQ→店舗への情報共有 |
| 設定 | ロール・表示制御の基盤 |

### PoCでは補助/任意（あれば検証幅が広がる）

| データ | 理由 |
|---|---|
| 売上/未払い | hacomonoとの重複確認が必要。補助的に確認 |
| 在庫 | 現場ニーズ次第。PoC店舗と合意して判断 |
| 応援掲示板 | FC本部との連携価値検証に有効 |
| カウンセリング記録 | 継続率向上への貢献度確認。PoC時は最小入力 |

### PoCでは扱わない/将来検討

| データ | 理由 |
|---|---|
| FC精算 | FCモデル・契約形態の確定が先 |
| 顧客チャット | 高リスク。本導入後に設計 |
| 本番API連携 | hacomono APIの利用可否確認が先 |
| kintone完全代替 | 段階的移行。PoCではTwinCoachを補助レイヤーとして使う |

## 5. データ保存方針

| 方針 | 内容 |
|---|---|
| 個人情報の最小化 | PoCでは本番個人情報を必要最小限にする。デモデータ・匿名データを優先 |
| CSV/限定データで検証 | 本番DB化する前に、CSV形式で取り込み・表示・分析を検証する |
| 既存ツールを止めない | hacomono/kintoneはPoC中も継続稼働。TwinCoachは補助レイヤーとして位置付ける |
| 保存対象の確定 | 本導入前に、どのデータをTwinCoachに保存し、どのデータを外部参照にするかを決める |
| 外部参照の最小化 | API連携後も取得項目を必要最小限にし、TwinCoach側にコピーするデータを絞る |
| ログ設計 | 操作ログ・連携ログは本導入前に要件を確定し、設計する |
| 削除方針 | 論理削除（無効化/アーカイブ）を基本とし、物理削除は原則行わない |

## 6. テーブル設計時の注意点

| 項目 | 内容 |
|---|---|
| 会員IDとhacomono ID | hacomono IDと紐づけられるよう `external_id` 列を持つ設計を検討する |
| 店舗ID | `storeId`（キャメルケース）で統一。DB上は `store_id`（スネークケース）|
| トレーナーID | 現状は名前文字列（trainerId未設計）。`trainer_id` への移行が本導入前の課題 |
| セッションと種目の分離 | 現状は `menuSummary`（テキスト）。本導入では `session_exercises` として正規化 |
| タスクの紐付け | 会員ID・店舗ID・担当者・ステータス・優先度を必ず持つ。自動生成フラグ（isAutoGenerated）も必要 |
| カウンセリングの時系列 | 1会員に複数レコードを持てる構造（memberId + date でソート）|
| リスクスコアの計算元分離 | スコア値（結果）と計算根拠（reasons配列）を分けて保存する |
| CSVインポート履歴 | ファイル名・件数・実行者・日時・ステータスを記録する |
| API連携ログ | 取得日時・取得件数・エラー内容を記録する |
| 削除の代替 | `deleted_at` 列または `status: "archived"` で論理削除を実装する |

## 8. 本導入前に確定すべきこと

| 項目 | 内容 |
|---|---|
| 正とするデータ元 | 会員・売上・予約はhacomono正とするか、TwinCoach正とするかを決める |
| テーブル定義 | 各テーブルの列名・型・制約・インデックスを確定する |

| CRUD権限 | ロールごとに操作可能な範囲を実装レベルで定義する |
| バリデーション | 入力値のバリデーションルールを定義する |
| 削除/アーカイブ方針 | 論理削除か物理削除か、保存期間を定義する |
| CSVインポート仕様 | 対応フォーマット・エラー処理・重複チェックルールを確定する |
| API連携仕様 | hacomono APIの取得項目・頻度・エラーハンドリングを確定する |
| 操作ログ方針 | 記録対象アクション・保存期間・閲覧者を定義する |

| 個人情報取り扱い方針 | プライバシーポリシー・同意取得・第三者提供範囲を確定する |

## まとめ

TwinCoachでは多くのデータを扱う可能性があるが、PoCでは会員・セッション・タスク・LTV/リスク・CSVインポートなど価値検証に必要な範囲に絞る。本導入前には、テーブル定義・CRUD権限・データ取得元・保存責任範囲を確定し、hacomono/kintoneとの役割を明確にする。
