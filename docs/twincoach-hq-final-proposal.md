# TwinCoach 本部向けPoC提案資料

作成日：2026-06-08  
対象：井上さん・濱口さん・林さん・本部

---

## 1. 提案の目的

| 項目 | 内容 |
|------|------|
| この提案の性格 | TwinCoachをいきなり全社導入する提案ではない |
| 提案内容 | まず1〜2店舗でPoCを行い、現場・オーナー・本部に価値があるかを検証する |
| 既存ツールとの関係 | hacomono/kintoneを置き換えるのではなく、既存情報を退会予防・LTV改善・現場行動に変換する補助レイヤーとして使う |

---

## 2. ELEMENTの課題仮説

- 会員情報・セッション記録・退会兆候が分散しており、一元把握ができていない
- 現場ごとに記録品質がばらつき、データの信頼性にムラがある
- 本部/オーナーが高リスク会員を早期に把握しづらく、対応が後手になりやすい
- 情報はあっても「次に何をするか」が現場行動に落ちにくい
- 管理業務がスタッフの負担となり、本来割くべきリソース（顧客対応・トレーニング指導）に集中しづらい
- 属人化によりサービス品質が一定になりにくく、店舗間・スタッフ間で差が出る

---

## 3. TwinCoachの役割

| ロール | できること |
|--------|-----------|
| 本部 | 全店舗のLTV・リスク傾向・店舗状況を横断把握 |
| オーナー | 管轄店舗の売上・リスク会員・トレーナー状況を確認 |
| 店舗 | セッション入力・会員詳細・介入タスクで現場行動に変える |
| SV | 店舗別課題と支援優先度をデータに基づいて判断 |
| TwinCoach全体 | 情報を保存するだけでなく、次の行動に変換するプラットフォーム |

---

## 4. PoCで検証すること

| 評価軸 | 確認内容 | 判断基準 |
|--------|----------|----------|
| 現場利用性 | スタッフが日常業務の中でTwinCoachを実際に使えるか | 継続利用率・利用頻度 |
| 入力負担 | セッション入力や会員情報更新が現場にとって重すぎないか | 入力完了率・現場フィードバック |
| 介入タスクの有用性 | タスクが実際の行動に繋がるか、内容は適切か | タスク完了率・現場評価 |
| 会員状態/退会予防の見える化 | 退会リスク・会員状態が把握しやすくなるか | リスク会員検知数・対応件数 |
| 本部/オーナーの判断材料 | ダッシュボードが実際の判断に使えるか | 閲覧頻度・フィードバック |
| CSV/API連携必要性 | CSVでPoC運用できるか、APIが必要か | データ更新頻度・CSV運用コスト |
| 権限/セキュリティ運用 | ロール別のデータスコープ制御が実運用に耐えるか | 権限設定ミス件数・セキュリティ指摘 |

---

## 5. PoCスコープ

- **対象**：1〜2店舗（ELEMENTグループ内）
- **期間**：2〜4週間
- **データ**：CSV/限定データで運用（個人情報最小化）
- **API連携**：PoC後に必要性を確認してから判断
- **既存運用**：hacomono/kintoneは止めない、並行運用
- **目的**：現場価値と導入リスクを小さく確認する

---

## 6. PoCで使う主な画面/機能

| 画面/機能 | 利用者 | 目的 |
|-----------|--------|------|
| HQダッシュボード | 本部 | 全店舗のLTV・リスク・売上状況を把握 |
| LTV管理 | 本部/オーナー | 会員LTV・解約リスクを一覧確認 |
| CSVインポート | 本部/管理者 | hacomonoデータをTwinCoachに取り込む |
| オーナーダッシュボード | オーナー | 管轄店舗の状況を確認 |
| 介入タスク | 店舗/オーナー | 高リスク会員への行動を管理 |
| 会員詳細 | 店舗 | 会員情報・セッション履歴・リスク状態を確認 |
| セッション入力 | 店舗 | トレーニング内容・状態変化を記録 |
| お知らせ | 全ロール | 本部からの連絡・更新通知を受け取る |
| 設定 | 管理者 | ロール・店舗・ユーザーを管理 |

---

## 7. CSV/API方針

- **PoC開始時点ではhacomono API連携を行わない**
- まずCSV/限定データで小さく検証する
- PoC中に必要なデータ項目と更新頻度を確認する
- PoC後にhacomono API連携の範囲・費用・権限・セキュリティを整理する
- API連携は目的ではなく、CSV手動更新作業を削減するための手段として位置づける

---

## 8. スモールスタート方針

- 最初から全店舗導入しない
- クリティカルな既存業務（hacomono予約・kintoneカルテ等）を止めない
- カルテなど停止すると現場が困る機能は最初から置き換えない
- 入力負担が低く、リスクが小さい範囲から検証する
- 不具合・使いにくさが判明した場合は既存運用に戻せる体制を保つ
- 高リスク機能（精算・FC連携・顧客チャット）は別フェーズで検討

---

## 9. 高リスク機能の扱い

| 機能 | 方針 |
|------|------|
| hacomono API本番連携 | PoC後に必要性を確認してから判断 |
| kintone完全代替 | 本導入後の将来検討。PoC中は置き換えない |
| FC精算機能 | 将来機能として別見積もり。今回のスコープ外 |
| 顧客チャット/連絡機能 | 運用ハードルが高いため後回し |
| 顧客個人情報/売上/精算に関わる機能 | 設計・契約・セキュリティ整理後に検討 |

## 11. 料金の考え方

- **PoC**：無料または低額（費用対効果を確認するフェーズ）
- **本導入**：店舗数課金＋月額課金が基本
- **費用区分**：初期設定費・月額保守費・追加開発費は分けて整理
- **別見積もり対象**：API連携、FC精算機能、顧客チャット、大規模追加開発
- **最終価格**：PoC範囲・対象店舗数・保守範囲・追加開発内容で調整
