# TwinCoach PoC評価指標

> バージョン：2026-06-06  
> 対象：林さん提案・井上さん＋濱口さん共有・PoC結果報告用

---

## 結論

| 方針 | 内容 |
|------|------|
| **PoCの目的** | TwinCoachが現場・オーナー・本部に価値を出せるかを確認すること |
| **評価の5軸** | 現場利用／入力負担／退会予防・見える化／本部/オーナー判断材料／データ連携必要性 |
| **PoC中の姿勢** | 完璧な効果測定を狙うのではなく、本導入判断に必要な材料を集める |
| **API連携・全店舗展開の判断** | PoC結果を見て判断する。PoC中は行わない |

## 1. 評価軸の全体像

| 評価軸 | 目的 | 主な確認内容 | 判断に使う相手 | PoC後の判断 |
|--------|------|-------------|---------------|-------------|
| 現場利用性 | 現場が実際に使えるかを確認する | 画面を開いているか、入力が継続しているか | 店舗スタッフ・トレーナー | 継続利用に進むか否かの基本判断 |
| 入力負担 | 入力作業が現場の許容範囲に収まるかを確認する | 入力時間・操作ステップ・不満の有無 | 店舗スタッフ・トレーナー | 画面/入力項目の改善要否の判断 |
| 介入タスクの有用性 | タスクが現場の行動につながるかを確認する | タスク確認率・対応率・現場の体感評価 | 店舗スタッフ・トレーナー | 介入タスクの継続・改善・廃止の判断 |
| 会員/退会予防の見える化 | リスク会員を早期発見できるかを確認する | 高リスク会員の確認件数・見落としの有無 | 店舗・オーナー | 退会予防への貢献度の評価 |
| 本部/オーナーの判断材料 | ダッシュボードが意思決定に使えるかを確認する | 閲覧頻度・判断の変化・見たい情報との一致度 | オーナー・本部/SV | 継続的な閲覧・活用の判断 |
| CSV/API連携必要性 | CSVで運用が成立するか、API連携が必要かを確認する | CSV運用での困りごと・不足項目 | 本部・濱口さん | API連携範囲・優先度の決定 |
| セキュリティ/権限運用 | 権限設計が現場運用で問題ないかを確認する | 権限超過・個人情報への懸念の有無 | 本部・TwinCoach側 | 本導入前の権限仕様詳細化の判断 |
| 継続利用可能性 | PoC終了後も使い続けたいと感じるかを確認する | 継続利用意向・改善要望の方向性 | 全ロール | 本導入判断・契約/保守体制整備への移行判断 |

## 2. 定量指標

| 指標 | 測定方法 | 目安 | 評価対象 | 備考 |
|------|---------|------|---------|------|
| セッション入力利用率 | 対象期間のセッション総数に対する入力済み件数の割合 | 50%以上で記録できていれば合格 | 店舗スタッフ・トレーナー | 100%を目標にしない。まず「使い始められるか」を優先する |
| 1件あたり入力時間 | 現場スタッフへのヒアリング・体感時間の確認 | 1件3分以内を目安 | 店舗スタッフ・トレーナー | ストップウォッチ測定は不要。体感で「重い/軽い」が確認できれば十分 |
| 介入タスク確認回数 | PoC期間中にタスク一覧画面を開いた延べ回数 | 週1回以上確認があれば合格 | 店舗スタッフ・トレーナー | 確認回数はサーバーログまたはヒアリングで把握する |
| 介入タスク対応率 | 未対応から対応中/完了に進んだタスクの割合 | 対応中/完了に進んだものが50%以上 | 店舗スタッフ・トレーナー | 「対応した」ではなく「ステータスを変えた」かどうかで計測する |
| 未対応タスク残数 | PoC終了時点で未対応のままのタスク件数 | 高優先タスクの未対応残数が0〜2件 | 店舗スタッフ | 残数が多い場合、タスク生成の精度・通知の仕組みを見直す |
| 高リスク会員の確認人数 | 高リスク判定会員のうち、担当スタッフが確認した件数 | PoC中に1人以上の高リスク会員を確認し行動につながること | 店舗スタッフ・オーナー | 「見て知った」だけでも価値として認める |
| オーナー/本部ダッシュボード確認回数 | PoC期間中のオーナー/本部ダッシュボードへのアクセス延べ回数 | 週1回以上の確認があれば合格 | オーナー・本部/SV | 確認頻度が増えるほど判断材料として機能していることを示す |
| CSV取り込み回数 | PoC期間中にCSVインポートを実施した回数 | 1回以上の成功実績があること | 本部・TwinCoach側 | 取り込み頻度よりも「成功したか」「運用になじむか」を確認する |
| CSVエラー件数 | 取り込み時に発生した重大エラーの件数 | 重大エラー（データ消失・不整合）0件を目標 | 本部・TwinCoach側 | 軽微な警告は許容。データ保全を最優先に確認する |
| 現場からの改善要望数 | PoC中に収集した改善提案・不満の件数 | 件数の多少より「具体的な要望が出ているか」を評価する | 全ロール | 要望ゼロは「使っていない」サインの可能性があるため注意する |

## 3. 定性指標

| 指標 | 確認方法 | 確認する相手 | 判断基準 |
|------|---------|-------------|---------|
| 現場スタッフが使いやすいと感じるか | 週次ヒアリング・簡易アンケート | 店舗スタッフ・トレーナー | 「使いにくい」より「こうすれば使える」という前向きなコメントが出ている |
| 入力項目が多すぎないか | ヒアリング・入力完了率の確認 | 店舗スタッフ・トレーナー | 「記録すべき項目が明確で、余計な入力が少ない」と感じている |
| 会員状態を把握しやすいか | 会員詳細・ダッシュボードを見た際の反応を確認 | 店舗スタッフ・オーナー | 「この会員の状態が一目で分かる」という発言が出ている |
| 介入タスクが行動につながるか | タスク対応後の行動内容をヒアリング | 店舗スタッフ・トレーナー | タスクを見て実際に会員へ声をかけた・連絡した事例が1件以上ある |
| オーナーが管轄店舗を把握しやすいか | オーナーダッシュボード確認後のヒアリング | オーナー | 「以前より店舗状況を掴みやすくなった」という評価が得られる |
| 本部が店舗課題を判断しやすいか | 本部ダッシュボード確認後のヒアリング | 本部/SV・井上さん | 「ここを見れば店舗への指示が出しやすい」という評価が得られる |
| CSV運用でPoCが成立するか | CSV取り込みの手順・頻度・手間の確認 | 本部・濱口さん | 「毎週CSVを更新しても許容できる手間感」と感じている |
| API連携すべき項目が明確になるか | PoC終了時のヒアリング・記録 | 本部・濱口さん・TwinCoach側 | 「この項目はCSVでは追いつかない」「ここはAPIがあれば楽になる」という具体候補が出ている |

## 4. ロール別の評価観点

| ロール | 評価する内容 | 主な確認画面 | 成功条件 | 確認頻度 |
|--------|------------|------------|---------|---------|
| 店舗スタッフ | セッション入力のしやすさ・介入タスクの使いやすさ・会員状態の把握 | セッション入力・会員一覧・会員詳細・介入タスク | 入力が継続できていて、介入タスクに1件以上対応している | セッションのたびに利用。週次でフィードバックを収集 |
| トレーナー | 担当会員のセッション記録・タスク確認・会員状態の把握 | セッション入力・会員詳細・介入タスク | 担当会員のセッションが入力できていて、タスクを確認している | セッションのたびに利用。週次でフィードバックを収集 |
| オーナー | 管轄店舗の状況把握・高リスク会員の確認・判断材料としての有用性 | オーナーダッシュボード・管轄店舗詳細・会員一覧 | 週1回以上ダッシュボードを確認し「役に立つ情報がある」と感じている | 週1〜2回の確認。PoC中盤・終盤にヒアリング実施 |
| 本部/SV | 全体進捗の把握・店舗課題の発見・CSV/データ連携の確認 | HQダッシュボード・LTV・CSVインポート・店舗詳細 | ダッシュボードで店舗への指示が出せる・API連携候補が整理できている | 週1回の確認。PoC全体を通じて進捗管理を担う |
| TwinCoach側 | CSV取り込みの安定稼働・不具合対応・フィードバック反映 | 管理画面全般・CSVインポート・ログ | 重大なバグがない・CSV取り込みが成功している・フィードバックが収集できている | 毎日確認。週次でフィードバックまとめと対応判断を実施 |

## 5. PoC成功条件

### 最低限成功（PoCとして成立している状態）

- 対象店舗で画面を開ける（ログイン・ナビゲーションが機能している）
- セッション入力が一部でも運用できている
- 介入タスクを確認できている
- 大きな運用停止・重大バグが発生していない
- CSV/限定データで検証環境が動いている

### 標準成功（PoCとして価値を確認できた状態）

- セッション入力がPoC期間中に対象セッションの50%以上で使われている
- 現場が入力負担を「許容できる」と評価している
- 介入タスクが現場の行動（声がけ・フォロー）につながった事例がある
- オーナー/本部が「見る価値がある」と評価している
- API連携すべき項目の候補が1〜2項目以上整理できている

### 高評価（本導入・API連携の具体検討に進める状態）

- 現場が「PoC後も使い続けたい」と感じている
- 本部/オーナーが判断材料として積極的に活用している
- 退会予防・フォロー対象の早期発見に役立った事例がある
- 本導入に向けた具体的な改善要望・追加機能の要望が整理されている
- API連携の必要性・優先項目・費用確認に進める材料が揃っている

## 6. PoC失敗/保留条件

以下の状況が複数重なる場合、PoCを一時停止し、原因整理と改善方針の合意を優先する。

| 状況 | 対応方針 |
|------|---------|
| 入力負担が大きすぎる（「使いたくない」という声が多数） | 入力項目の削減・UI改善・運用フローの見直しを先行して行う |
| 現場が画面を開かない・使わない | 使わない理由をヒアリングし、動線・説明・操作の簡略化を検討する |
| 介入タスクが行動につながらない（見るだけで終わる） | タスクの内容・表示方法・通知タイミングを見直す |
| 本部/オーナーが見たい情報とズレている | ダッシュボード項目・表示優先度を再整理する |
| CSVデータの準備が重すぎる（毎週CSV更新が難しい） | 更新頻度を下げる・項目を絞る・CSV準備担当を決める |
| 権限/個人情報の懸念が大きく解消できない | 権限仕様の詳細化・個人情報取り扱いルールの整備を先行させる |
| 既存運用（hacomono/kintone）への影響が許容できない | 並行稼働の方法を再確認し、既存業務を守る設計に戻す |

## 9. 本導入/API連携へ進む判断基準

以下が揃ったタイミングで、本導入・API連携の具体検討に進む。

| 判断軸 | 判断できる状態 |
|--------|--------------|
| 現場利用が一定以上ある | スタッフ・トレーナーがPoC期間中に継続して利用している実績がある |
| 入力負担が許容範囲 | 現場が「続けられる」と評価している（「重い」という声が支配的でない） |
| 介入タスクが行動につながる | タスクを見て実際にフォローアクションにつながった事例が確認できている |
| 本部/オーナーが継続的に見たい情報がある | ダッシュボードを積極的に確認し、「ここを改善すれば使い続けたい」という評価がある |
| API連携すべき項目が明確 | 「CSVで困った・自動化したい」という具体的なデータ項目が整理されている |
| 権限/セキュリティ上の大きな懸念が整理可能 | PoC中に発見したリスクに対して、本導入前の対応方針が合意できている |
| 契約/費用/保守の論点整理に進める | hacomono費用・保守体制・責任分界・契約条件の相談を開始できる状態にある |

## 10. 佐々木さんフィードバックの反映

| フィードバック | PoC評価指標への反映 |
|--------------|-------------------|
| PoCは低リスク範囲から始める | 評価指標もセッション入力・介入タスク・ダッシュボード確認など低〜中リスク機能に絞って定義した |
| クリティカルな既存機能は止めない | 失敗条件に「既存運用への影響が許容できない」を含め、並行稼働の継続を前提とした |
| 効果測定だけでなく、運用負荷と導入リスクも評価する | 定性指標に「入力負担」「CSV運用の許容感」を含め、数値だけで判断しない設計にした |
| 本導入前に設計/契約/環境整理が必要 | 本導入判断基準に「契約/費用/保守の論点整理に進める」を明示した |
| API連携はPoC結果を見て必要性を判断する | API連携候補はPoC中に収集した「CSV運用で困った項目」から導出する設計にした |

## まとめ

TwinCoachのPoCは、機能の完成度を評価する場ではなく、現場が使えるか、入力負担が許容できるか、退会予防や本部判断に役立つかを確認する場とする。PoC結果をもとに、本導入・API連携・契約/保守体制へ進むかを判断する。
